# Reth 目标

### 为什么要构建这个客户端？

我们构建 Reth 的目标，除了提高客户端多样性外，还要创建一个在以下各个维度上都达到极致的客户端：

- 性能 (Performance)
- 可配置性 (Configurability)
- 开源友好性 (Open-source friendliness)

---

## 性能

### 为什么性能很重要？

这对每个人来说都是共赢：
- 普通用户和开发人员受益于 RPC 性能，从而获得响应更快的应用程序和更快的反馈。
- 家庭节点运营商受益于更快的同步时间。
- 所有运营商的成本都降低了，无论是存储成本，还是能够从同一个节点服务更多请求。
- 搜索者能够运行更多模拟。

### 需要解决哪些性能瓶颈？

**优化状态访问**

给定交易在处理过程中经历的流水线大致如下：

RPC -> EVM -> 缓存 -> 编解码器 -> 数据库 (DB)

Reth 的首要目标之一是尽量减少此流水线的延迟并最大化吞吐量（例如：请求并发）。

为什么？这对每个人来说都是共赢。RPC 提供商可以满足更令人印象深刻的 SLA，MEV 搜索者变得更有效率，家庭节点同步更快，等等。

这条流水线中最大的瓶颈不是 EVM 解释器本身的执行，而是访问状态和管理 I/O。因此，我们认为最大的优化空间在于最接近数据库层的地方。

理想情况下，我们可以实现如此快速的运行时操作，从而避免在磁盘上存储某些内容（例如交易收据），而是能够即时生成它们 - 从而最大限度地减少磁盘占用空间。

---

## 可配置性

### 为什么可配置性很重要？

**对权衡的控制**

对于客户端，几乎任何给定的设计选择或优化都带有其自身的权衡。因此，我们的长期目标不是代表所有人做出武断的决定，因为某些用户会受到负面影响并放弃使用这个本来可能很棒的客户端。

**配置文件 (Profiles)**

我们的目标是促进社区开发的配置预设的创建，这些预设适用于各种用户画像，例如归档节点、RPC 提供商、MEV 搜索者等。

**扩展到 EVM 兼容的 L1 和 L2**

可配置设计的另一个结果是能够快速扩展客户端以支持其他 EVM 兼容的 L1 和 L2，在保持性能的同时实现创新。

### Reth 如何实现可配置性？

**模块化和泛型**

我们优先考虑 Reth 的模块化设计，在通用接口之上采用合理的（且零成本的！）抽象。我们希望其他人能够快速轻松地扩展或调整实现以满足他们自己的需求。

---

## 开源友好性

### 为什么开源友好性很重要？

维护客户端实现非常*困难*。引进人才和维持工作流的势头是一个众所周知的挑战。因此，我们采取开源优先的方法，以确保 Reth 的开发可以由社区推进。

我们希望尽可能深思熟虑地与以太坊社区形成反馈闭环，不仅要让贡献 Reth 变得容易，而且实际上要积极*鼓励*这样做。

我们的目标是，即使是没有 Rust 经验、没有运行节点经验的社区成员，仍然能够为项目做出有意义的贡献，并在过程中积累专业知识。

### Reth 如何支持开源贡献？

**文档**

不言而喻，详尽彻底的文档是必须的。文档应提供有关客户端设计和实现以及贡献过程的完整背景信息，并且任何具有以太坊基础知识的人都应该能够访问。

**问题追踪**

客户端内正在（和不在）进行的每项工作都应得到相应跟踪，以便社区中的任何人都能掌握开发状态。这清楚地表明了哪里需要什么样的帮助。
